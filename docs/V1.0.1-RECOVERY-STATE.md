## Why v1.0.1 exists

The public v1.0 release was intentionally frozen at TB031.

After that freeze, additional UI/runtime work continued under TB032. The Steam Workshop proof-of-concept initially used the exact frozen TB031 PAK, so the Workshop-only runtime correctly reproduced the older v1.0 Character UI. This was not lost work: the later fixes were never merged back into TB031.

The current Workshop-only regression is therefore not a missing-payload problem. The strongest current hypothesis is **runtime load order / JavaScript module caching**:

- the Workshop PAK is mounted dynamically by the mod bootstrap during game startup;
- the main-menu hover module can be imported/instantiated before or during the mod bootstrap path;
- if `CharacterHorverPanel.js` / `EquipDescItem.js` are already loaded into the Puerts/CommonJS module cache before the PAK override becomes visible, mounting the corrected files afterward will not replace the already-loaded module objects;
- `CharacterInfoPanel.js`, used later when entering the Character screen, can still resolve from the mounted PAK and therefore shows the repaired Gear/Skills layout.

PROBE078 verified this hypothesis at runtime.

However, the main-menu hover visually regressed to the old layout.

Therefore the simplified sequence is **not equivalent** to BUILD081. One or more operations that looked diagnostic in BUILD081 are behaviorally significant in this runtime. The leading candidates are:

- pre-requiring the cached old modules before reload;
- resolving/confirming their exact cache entries through `puerts.getModuleByUrl`;
- or the combination/order of those operations.

The release bootstrap must not simplify these steps until each is independently proven unnecessary.

The safest current path is to preserve the exact known-good BUILD081 execution sequence for the v1.0.1 release candidate, even if that means retaining harmless diagnostic-style cache lookups/logging.
