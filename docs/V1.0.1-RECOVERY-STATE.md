# v1.0.1 Recovery State

This document records the recovery/freeze boundary for the first post-v1.0 patch release.

## Why v1.0.1 exists

The public v1.0 release was intentionally frozen at TB031.

After that freeze, additional UI/runtime work continued under TB032. The Steam Workshop proof-of-concept initially used the exact frozen TB031 PAK, so the Workshop-only runtime correctly reproduced the older v1.0 Character UI. This was not lost work: the later fixes were never merged back into TB031.

Result:

**The complete main-menu hover implementation survived unchanged from Candidate 003C through Candidate 004U.**

The current Workshop-only regression is therefore not a missing-payload problem. The strongest current hypothesis is **runtime load order / JavaScript module caching**:

- the Workshop PAK is mounted dynamically by the mod bootstrap during game startup;
- the main-menu hover module can be imported/instantiated before or during the mod bootstrap path;
- if `CharacterHorverPanel.js` / `EquipDescItem.js` are already loaded into the Puerts/CommonJS module cache before the PAK override becomes visible, mounting the corrected files afterward will not replace the already-loaded module objects;
- `CharacterInfoPanel.js`, used later when entering the Character screen, can still resolve from the mounted PAK and therefore shows the repaired Gear/Skills layout.

PROBE078 verified this hypothesis at runtime.

## PROBE078 — Workshop/Puerts cache behavior confirmed

BUILD077 was delivered byte-for-byte through Workshop and imported into the live mod directory:

- Candidate 004U PAK SHA256: exact PASS

The built-in `puerts` module exposes:

- `genRequire`
- `getModuleBySID`
- `getModuleByUrl`
- `loadModule`
- `registerBuildinModule`

After the Candidate 004U PAK mounted successfully with order 100 / mount point `../../../`, requiring the two target hover modules returned functions that did **not** contain the preserved TB032 implementation markers:

- `EquipDescItem`: no `TB032 Candidate 003C` marker
- `EquipDescItem`: no `keep category + item as one unit` marker
- `CharacterHorverPanel`: no `TB032 Candidate 003A` marker
- `CharacterHorverPanel`: no `mTB032EquipInfoSizeBox` marker
- `CharacterHorverPanel`: no `WrapBox` marker

The menu hover remained visually in its old/pre-fix layout.

**Conclusion: the early hover modules are already cached from the pre-Workshop/vanilla load before the Workshop PAK mounts.** Mounting the correct 004U PAK afterward does not invalidate that module cache.

This is now a confirmed cache/load-order problem rather than a hypothesis.

The next investigation must be narrowly scoped to:

1. identify the exact PuerTS module-cache keys for the two target hover modules;
2. understand the runtime semantics/signatures of `puerts.forceReload`, `puerts.genRequire`, and related functions in this shipped build;
3. reload only the required hover modules (and, if needed, their direct consumer) after the PAK mount;
4. avoid a global cache flush unless a targeted approach is proven impossible.

## v1.0.1 freeze gate

Before v1.0.1 is published:

1. Preserve Candidate 004T and Candidate 004U by their verified SHA256 values.
2. Keep Candidate 004U as the current late-TB032 base because its Character Gear/Skills improvements are validated.
3. Treat pre-mount caching of the hover modules as confirmed by PROBE078.
4. Identify their exact PuerTS module-cache keys and direct consumer chain.
5. Validate a targeted post-mount reload strategy using `puerts.forceReload` / `genRequire` without globally flushing unrelated modules.
6. If necessary, add a narrowly scoped Workshop bootstrap solution for early-loaded hover modules without changing the validated 004U payload semantics.
7. Run a Workshop-only regression pass covering:
   - main-menu character hover and category/name fit
   - Character Gear
   - Character Skills
   - Skill keyword/mastery presentation
   - Fashion/Nickname spacing
8. Freeze the resulting Workshop-compatible artifact immutably as the v1.0.1 source.
9. Record final PAK and release ZIP SHA256 values.
10. Only then update the public release/tag and Workshop metadata.

Do not reconstruct the hover fix from memory while the exact implementation is preserved.
